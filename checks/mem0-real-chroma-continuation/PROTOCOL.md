# Real Chroma continuation controls

Youngseok Oh × Zero | 26 September 2026

The previous recipient-revision check ran a real populated FAISS case but used mocked Chroma responses. This follow-up checks a real local Chroma collection through the declared LangChain integration. It supplies no runtime fix and does not assume that a failure would be caused by the latest listing change.

Pin Mem0 fork revision `127bb79725aeb09d70e58620fd1d88476abf9aca`. Compare its exact adapter with `cec74a8ebf5a9d6724104d4867868da118b58205`'s adapter, keeping the rest of the checkout, tests and dependencies unchanged. This establishes whether a measured difference depends on that file revision; it does not date a defect's original introduction.

Use langchain 0.3.30, langchain-community 0.3.31, langchain-core 0.3.86 and Chroma 1.5.9. These LangChain versions match the preceding run, and the Chroma version was named in the original report. They are a pinned review environment, not a claim to use the newest release of every package. The remaining dependency resolution is recorded.

Eight predetermined cases per adapter: populated listing; known-ID retrieval; known-ID direct adapter deletion; empty and populated Memory.get_all; empty and populated Memory.delete_all; and native scoped Chroma deletion. Each case has a fresh collection. Populated collections contain explicit numeric embeddings and four synthetic documents with known IDs: Alice three, Bob one. Compare raw IDs, documents and metadata before/after, not just the response string. A scoped delete should leave Bob unchanged. No embeddings are generated by a model.

The Memory fixture is the unchanged recipient helper, with real construction/methods but mocked LLM/embedder factories, configuration, history and telemetry. Only its vector store is replaced by the real Langchain/Chroma object. We record method ownership and the actual get_by_ids implementation to make a dependency capability boundary diagnosable. No store enumeration, known-ID read or deletion is mocked. This is not a full production Memory configuration, live hosted service, asynchronous surface or full-suite test.

Each behavioral assertion is recorded whether it passes or fails. The workflow passes if all 16 selected observations finish, no case is skipped or has a fixture/collection error, and the source is restored. It does not require every functionality expectation to pass. Retain any failure traceback and all final store contents. No result has been inspected before committing this protocol and the test.

One bounded CPU workflow; no existing deployment, user memory, credentials, paid model endpoint, or model weights. Network access is for checkout/dependency setup. Python socket/DNS calls are blocked in measurement subprocesses; this is not an OS sandbox. No upstream issue, PR or automatic message is part of execution. Subsequent feedback must respect the original issue owner and project contribution gate.
