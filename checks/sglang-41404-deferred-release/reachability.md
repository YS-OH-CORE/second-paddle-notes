## Why an AbortReq can precede transfer-failure cleanup

1. The PP loop ingests this iteration's requests before collecting preallocation and transferred-ID consensus. The transferred-ID snapshot occurs at line 436. [Loop ordering](https://github.com/sgl-project/sglang/blob/d574752ef39eb3ef73f87c40dca95d76222f9483/python/sglang/srt/managers/scheduler_pp_mixin.py#L388-L441)
2. Later in that iteration, `process_prealloc_queue` runs before `process_decode_transfer_queue`. Its `pop_preallocated` call sends metadata and appends the request to its successful-preallocation list without re-polling the receiver after `send_metadata`. It then extends the transfer queue with those requests. [PP processing order](https://github.com/sgl-project/sglang/blob/d574752ef39eb3ef73f87c40dca95d76222f9483/python/sglang/srt/managers/scheduler_pp_mixin.py#L518-L533), [preallocation return](https://github.com/sgl-project/sglang/blob/d574752ef39eb3ef73f87c40dca95d76222f9483/python/sglang/srt/disaggregation/decode.py#L1695-L1721), [queue extension](https://github.com/sgl-project/sglang/blob/d574752ef39eb3ef73f87c40dca95d76222f9483/python/sglang/srt/managers/scheduler_pp_mixin.py#L1884-L1903)
3. A request newly added after the snapshot cannot occur in that earlier transfer-ID list. Other PP ranks intersect their own IDs with the previous stage's list; this operation cannot add a request absent from the previous list. The current consensus may instead refer to an even earlier microbatch, or not yet be available; neither case includes this newly added request. [Transfer-ID intersection](https://github.com/sgl-project/sglang/blob/d574752ef39eb3ef73f87c40dca95d76222f9483/python/sglang/srt/managers/scheduler_pp_mixin.py#L1849-L1872)
4. `process_decode_transfer_queue` resolves previously deferred releases, then passes `release_rids` to `pop_transferred`. `pop_transferred` explicitly skips a request absent from that list. Polling a newly failed receiver does not itself override this skip. Thus the newly admitted request can remain in the transfer queue across the iteration boundary. [Queue processing](https://github.com/sgl-project/sglang/blob/d574752ef39eb3ef73f87c40dca95d76222f9483/python/sglang/srt/managers/scheduler_pp_mixin.py#L1905-L1923), [membership filter](https://github.com/sgl-project/sglang/blob/d574752ef39eb3ef73f87c40dca95d76222f9483/python/sglang/srt/disaggregation/decode.py#L2615-L2643)
5. The next iteration again ingests requests before its transfer cleanup. `ingest_requests` synchronously dispatches received input. An AbortReq for a device-destination transfer-queue request calls `kv_receiver.abort()`; the host-staged early-continue branch does not apply. This is the concrete scheduler route by which an external abort may arrive before the transfer queue's forced-arm failure path. [Input dispatch](https://github.com/sgl-project/sglang/blob/d574752ef39eb3ef73f87c40dca95d76222f9483/python/sglang/srt/managers/scheduler.py#L2063-L2086), [device-transfer abort](https://github.com/sgl-project/sglang/blob/d574752ef39eb3ef73f87c40dca95d76222f9483/python/sglang/srt/managers/scheduler.py#L5524-L5544)

## Composed failure hypothesis

Mooncake's `send_metadata` sends sequentially to the bootstrap recipients. A ZMQ exception after an earlier successful send marks the receiver failed and returns before assigning `init_time`. This provides a source route to partial publication while `init_time is None`. The NIXL implementation has the same ordering, but the configuration argument above only needs Mooncake. [Mooncake publication](https://github.com/sgl-project/sglang/blob/d574752ef39eb3ef73f87c40dca95d76222f9483/python/sglang/srt/disaggregation/mooncake/conn.py#L2968-L3029), [NIXL publication](https://github.com/sgl-project/sglang/blob/d574752ef39eb3ef73f87c40dca95d76222f9483/python/sglang/srt/disaggregation/nixl/conn.py#L3234-L3309)

If the PP ordering above admits an AbortReq before queue failure cleanup, `abort()` calls `ensure_abort_notified()` without `force_arm=True`. With `init_time is None`, `_send_abort_notification` sends ABORT without registering the deferred-ack room, after which `abort_notified=True`. [Abort notification and arming](https://github.com/sgl-project/sglang/blob/d574752ef39eb3ef73f87c40dca95d76222f9483/python/sglang/srt/disaggregation/common/conn.py#L2016-L2069)

When the failed request eventually reaches `pop_transferred`, its forced-arm notification is conditional on `not abort_notified`. An already-notified request skips that call but still enters `_defer_release`. The ack recorder only adds acknowledgments for registered rooms. The inferred consequence is delayed reclamation until the timeout when a drain acknowledgment could otherwise have satisfied release. **This is an unexecuted interaction hypothesis, not confirmed corruption, a leak without a timeout, or a measured service impact.** [Failure cleanup](https://github.com/sgl-project/sglang/blob/d574752ef39eb3ef73f87c40dca95d76222f9483/python/sglang/srt/disaggregation/decode.py#L2676-L2704), [ack tracking](https://github.com/sgl-project/sglang/blob/d574752ef39eb3ef73f87c40dca95d76222f9483/python/sglang/srt/disaggregation/common/conn.py#L643-L663), [deferred release resolution](https://github.com/sgl-project/sglang/blob/d574752ef39eb3ef73f87c40dca95d76222f9483/python/sglang/srt/disaggregation/decode.py#L2778-L2841)
